sjbis design doc · cli + architecture · v0.4

A universal information plane
any tool can call.

SJBIS is one daemon, one CLI, and a thin AI layer that turns arbitrary questions from arbitrary callers into the right interaction for you — surfaced, ranked, deduped, and routed by rules you write in English.

TL;DR

Any process emits a single sjbis ask command with a question and an answer shape. A local daemon receives it, asks an LLM to fill in the gaps (urgency hints, the right renderer, identity, deduping), pushes it to your dashboard, and waits for an answer.

Your end of the contract: a typed answer comes back on the caller's chosen channel — stdout, exit code, webhook, or a file you watch. Or a timeout. Or a structured "muted" signal if your rules said to drop it.

01 The anatomy of a call

The hardest design choice is "what does the caller have to know?" The answer is: a question, an answer shape, and how to find them again. Everything else is either inferred by the AI router, defaulted, or written once in a config file.

~/projects/inbox-agent · sjbis ask
$ sjbis ask \ --question "Claim Tuesday's burrito as a business expense?" \ --yesno \ --agent-name "Postmaster" # required — drives SRC, glyph, rule-matching --instance "Gmail inbox" # optional — appended to SRC line --urgency 5 # 0..5, default 2 --blocking # the caller will wait --deadline 6m # auto-timeout, e.g. "90s", "2h", "tomorrow 9am" --detail "Receipt $14.20 at Cilantro. Meeting with Priya was on cal." \ --reply-to stdout # or `webhook:https://...`, `file:./out.json` --json # structured response { "id": "sjbis-7e2af19", "answer": true, "answer_label": "Yes, claim it", "answered_at": "2026-05-20T14:03:11Z", "latency_ms": 42118, "renderer": "yesno", "src": "Postmaster · Gmail inbox", "via": "dashboard · keyboard Y" }

Three things define every call:

  • The question — required, free text. Anything goes. The AI router reads it.
  • The answer shape — one of --yesno, --choices, --text, --number, --file, --diff, --ack, --pick, --schedule. Required, but if you skip it the AI guesses and adds "renderer_guessed": true on the response so callers can decide whether to trust it.
  • The agent name — --agent-name "OpenCode". Required. Stable across runs of the same caller; drives the SRC line, glyph, color, and rule-matching. Optional --instance tacks on per-session detail.
  • The reply channel — --reply-to. Default is stdout if you ran --blocking, otherwise a webhook. Non-blocking + no reply-to means you'll re-poll with the returned id.

04 Architecture

Six components. One process boundary (the daemon). Three roles for the LLM — each scoped tight enough to be replaceable.

Components

Ingress deterministic

CLI & SDK frontends, a Unix domain socket, and an optional HTTP listener for cross-machine callers. Validates flags, attaches the caller's auth token, applies --id idempotency, and pushes onto the queue. No LLM calls here — speed matters; a stuck ingress would block agents.

  • p50 enqueue latency < 5 ms; p99 < 30 ms
  • Rejects malformed shape (e.g. --number without --min/--max) before queueing
  • Auto-spawns the daemon on first call if missing

AI Router LLM × 1–3

Reads the question text and the calling source, and decides three things: renderer (only when missing or --guess-renderer), predicted urgency (used to break ties when callers under- or over-claim), and dedupe candidates (does this look like another open notification?).

  • Cached: identical (source, question) within 60s skips the LLM
  • Returns a confidence score; the caller's own --urgency wins on low confidence
  • Bypassed entirely when --privacy private

Rule Engine hybrid

Each rule is two layers: a natural-language line you wrote ("only family for the next hour") and a compiled JSON filter the daemon executes on every notification. The compiler is an LLM call run once at rule-write time; matching itself is deterministic boolean logic.

  • Rules can mute, snooze, re-prioritize, or auto-answer (e.g. always yes for < $50 reimbursements)
  • Time-scoped: "for the next 15 min" compiles to { until: <ts> }
  • Order matters; explicit allow beats implicit deny

Queue + Store SQLite

Single-writer SQLite database with a WAL. Two tables, basically: notifications (in-flight + history) and rules. Auditable, scriptable, backupable. The daemon is stateless beyond this.

  • Schema migrations live in the binary; auto-runs on start
  • Retention: history kept 30 days by default, configurable

Identity Store deterministic

Maps --agent-name to a stable glyph and OKLCH color (deterministic hash). The optional --instance string is rendered after the agent name in the SRC line but does not affect identity — so every "OpenCode" session shares the same avatar and matches the same rules. Override via sjbis identity set OpenCode --glyph ⌬ --color "#C7F33D".

  • No LLM — pure hashing on --agent-name
  • Identity is per-user, never broadcast
  • Card SRC line: "{agent-name} · {instance}"

Response Router deterministic

When the user answers, this component formats the response per the caller's --reply-to and delivers it. Three channels: write to a long-poll stdout, POST a webhook, or atomically write a file the caller is watching.

  • Retries webhooks with backoff up to --reply-deadline
  • Records the full answer trail (renderer, latency, via) in the store

Dashboard SSE client

The HTML/JS app you've seen. Subscribes to the daemon over Server-Sent Events for live updates, posts answers back via a small REST endpoint. The dashboard renders the renderer the AI router picked — it does not invent UI on its own.

  • Two clients planned: full browser dashboard, compact tray widget
  • Assumes daemon is reachable — if it isn't, the dashboard is useless anyway (no notifications to show)

LLM Provider OpenAI-compatible

The router talks to any OpenAI-compatible endpoint. Default: Fireworks (cheap, fast, hosts open-weight models like Llama 3.3 70B and Qwen). Anthropic and OpenAI work too. Local Ollama for fully-offline mode. Prompts are structured but not aggressively token-pinched; a router call is comfortably ~1–2k tokens.

  • Token budget: ~1.5k tokens / router call · ~$0.0003 on Fireworks Llama 70B
  • Hard cap: 3 LLM calls per ask (router + renderer-guess + dedupe)
  • Falls back to deterministic behavior on provider outage

05 Lifecycle of one ask

A blocking yes/no, from $ to answer, in eight steps. Steps marked AI involve an LLM; the rest are deterministic. Steady-state, an ask makes 1 LLM call (router classify), sometimes 0 when the cache hits, occasionally 2–3 when the caller asked the renderer to be guessed.

1
caller · code-agent
Caller emits the CLI command.

Question, answer shape, urgency, deadline, reply channel. Marshalled into a single JSON payload over the local socket.

sjbis ask --yesno -q "..." -u 4 -d 6m --blocking
2
ingress
Validate, auth, idempotency-check, enqueue.

Reject malformed shapes immediately. Look up --id in the store; if found and not stale, return the existing notification id. Otherwise create a new row in notifications and assign it.

3
ai router AI
One short LLM call: classify, predict urgency, find duplicates.

Prompt includes the question, the caller's source, the last ~10 open notifications (for dedupe), and the caller's claimed urgency. Returns structured JSON. If the model thinks this looks like an open notification with --mute-key match, the call updates that one instead of creating a new card.

4
rule engine
Apply your rules in order.

Each rule's compiled filter runs against the notification's fields. First match wins. The rule can: pass through unchanged, change urgency, mute, snooze until a time, or auto-answer with a default.

5
dashboard (push)
Server-sent event → card appears.

All connected dashboard clients receive the new (or updated) notification. Urgency 5 animates in to center; urgency 1–2 drifts into the field. Audio cue if enabled.

6
user
You answer.

Click, type, drag, or keyboard shortcut. The answer carries its renderer ("via: dashboard · keyboard Y") so the response is debuggable later.

7
response router
Format & deliver via the caller's chosen channel.

Stdout: write the JSON to the long-polled connection. Webhook: POST with retry. File: atomic rename onto the watched path. Exit-code: set the daemon's exit hint, which the blocked caller reads on disconnect.

8
store · audit
Persist the answer trail.

Latency, renderer, who answered, the question text, the answer text. Available via sjbis history and as the data behind the dashboard's "recent" rail.

05.5 Long-running agents vs ephemeral callers

SJBIS is called by two very different shapes of process, and the contract has to work cleanly for both.

Long-running · Hermes, OpenClaw, Postmaster

Run for hours or weeks. Fire many asks per session. Often need the answers to keep doing their job — Hermes can't reply to your kid on iMessage without asking what to say first. These are first-class clients of the daemon.

Ephemeral · cron, shell, one-shots

Boot, fire one ask, block on the answer (or webhook back), exit. Don't need persistent identity or long-lived state with the daemon. The contract is just "post and wait."

Long-running agents get four extras the contract has to accommodate:

1 · One-time registration, persistent identity

A long-running agent runs sjbis register on startup once and the daemon issues a scoped token. After that, every ask over the agent's lifetime is auth'd without per-call --auth-token. The token is bound to the agent's --agent-name: a Hermes token can only post as "Hermes" — it can't impersonate "OpenClaw".

~/agents/hermes · startup.sh
$ sjbis register \ --agent-name "Hermes" \ --glyph "♡" --color "#FF3D7F" \ --scopes "ask:fam,ask:friends" # tag-prefix allowlist { "agent": "Hermes", "token": "sjbis-tok-7d2af1e9...", "identity_locked": true } $ # now the agent loops, calling sjbis ask 50x/day, $ # reusing $SJBIS_TOKEN from this single registration.

2 · Persistent connection for many in-flight asks

Instead of spawning a fresh sjbis process for every question, long-running agents open a persistent connection to the daemon (gRPC over the Unix socket) and multiplex asks. That's how Hermes keeps 6 questions in-flight at once — chowder vote, sleepover, grocery list, two unread photos, and a calendar conflict — without 1500 fork()s a day.

3 · Answer-stream subscription

The agent subscribes to its own answer stream: sjbis subscribe --agent Hermes yields each answer as it lands. This is better than per-ask --blocking for two reasons:

  • You don't tie a thread to every outstanding question.
  • The agent can correlate answers back to whichever conversation they belong to via the --id field, so the iMessage thread the answer is for stays straight even if you answer them out of order on the dashboard.

4 · Health & backpressure

The dashboard shows liveness for each registered agent (when it last pinged, how many open asks, how many it dropped). If a long-running agent starts shouting — say it pushes 30 asks in 10 minutes — the daemon can apply backpressure: returning { throttled_until } instead of accepting, with a hint about which rule fired. The agent backs off; you don't drown.

Why does this matter for the diagram?

Two things move when you take long-running agents seriously: (a) the ingress isn't just a CLI parser — it has to host a persistent gRPC channel, and (b) the queue+store has a new field per notification, tag, which the agent uses to correlate answers back to whatever conversation, file, or thread the question was about. Both already in the box above; this section just names them.

06 The AI layer, with explicit scopes

The thing that makes SJBIS more than a notification queue is the AI layer — but it's also the most dangerous place to wave hands. Three scopes, three prompts, three failure modes. Anything else is deterministic.

Scope 1 — Routing & ranking

Run on every ask (unless --privacy private). One prompt, ~300 tokens in. Returns a small JSON envelope used to fill gaps and detect duplicates.

prompt · sjbis.router.classifyfireworks · llama-v3p3-70b-instruct · ~1.5k tok
SYSTEM You triage notifications headed for Stephen's information surfacer. Output JSON with fields: urgency_predicted (0..5) — what you'd set if the caller hadn't renderer_suggested (one of: yesno|multichoice|freetext|numeric| file|diff|ack|picklist|schedule) looks_like_id (id of an open notification this duplicates, or null) confidence (0..1) Do not editorialize. Do not rewrite the question. USER question: "Approve renaming getUser → fetchUser across 14 files?" caller_source: "OpenCode Session s7b3d11" caller_urgency: 3 open_notifications: - { id: "n-001", source: "iMessage via Hermes", q: "Clam chowder vote..." } - { id: "n-003", source: "OpenCode Session s7b3d11", q: "Approve adding test coverage..." } - ...
Good failure mode

Provider down or 5xx → the daemon falls back to the caller's claimed urgency, picks the renderer from the explicit flag, and skips dedupe. The notification still surfaces.

Bad failure mode (guarded against)

The model rewrites the question or invents an urgency 5 from a calm caller. We never substitute the model's text into user-visible fields; urgency_predicted only fires when caller confidence is low.

Scope 2 — Rule compilation

Run once when you write a rule. Translates one English sentence into a boolean filter the daemon evaluates per-notification with no further AI involvement. The compiled JSON is shown in the dashboard so you can audit it.

prompt · sjbis.rules.compilefireworks · llama-v3p3-70b-instruct · ~2k tok
SYSTEM Convert one English rule into a JSON filter. Schema: { match: { source?, agent?, urgency_min?, urgency_max?, question_includes? }, action: "surface" | "mute" | "snooze:<duration>" | "auto_answer:<value>" | "reprioritize:<0-5>", expires_at: ISO-8601 | null, // one-shot rules use this active_window: { start: "HH:MM", end: "HH:MM", tz: "…" } | null // daily recurring } Use the user's known agents (provided). Always emit a full ISO-8601 timestamp for one-shot rules — never a bare HH:MM. If the time is ambiguous (e.g. "at 3pm" without "today"), return { error: "ambiguous_time", suggestions: […] }. USER now: 2026-05-20T14:00:00-07:00 known_agents: [Postmaster, Hermes, OpenClaw, Sentinel, Chronos, Ledger, ...] rule: "Only family and texts from my kids for the next 15 minutes." ASSISTANT (expected) [ { match: { agent: ["Hermes"] }, action: "surface", expires_at: "2026-05-20T14:15:00-07:00" }, { match: { agent: ["*"] }, action: "mute", expires_at: "2026-05-20T14:15:00-07:00" } ]

Scope 3 — Renderer hinting (optional, only on --guess-renderer)

The CLI lets a lazy caller skip the answer-shape flag and just say "figure it out." The router suggests one in scope 1; for callers who pass --guess-renderer the router also synthesizes the metadata that shape needs (choices for multichoice, slot ranges for schedule). The user sees a (rendered by sjbis) tag on the card so you know it wasn't shaped by the calling tool.

Why so little AI?
Every additional LLM call is a chance to be wrong about Stephen's attention. The product promise is "anything can call sjbis" — that means the AI surface has to be cheap, fast, and explainable. The cards on the dashboard already commit to the caller's claimed shape and copy. The AI only fills in what the caller left blank, ranks among peers, and reads your English rules.

07 The rules language

Rules are how you bend the firehose. Three ways to write them:

  • Command bar in the dashboard — type English, see the chip appear, see the compiled JSON on hover.
  • CLI — sjbis rule add "anything from Dana is urgent".
  • Config file — ~/.config/sjbis/rules.toml for version-controllable rules.

A few realistic examples and what they compile to. Time-scoped rules always compile to a full ISO-8601 expiration — never bare HH:MM — so they can't quietly re-fire tomorrow.

Said (at 14:00 on 2026-05-20)
Compiled (rule + expires_at)
"Only family for the next hour."
[surface agent:fam; mute *]
expires_at: 2026-05-20T15:00-07:00
"Mute Slack until 3pm."
[mute source:"Slack via *"]
expires_at: 2026-05-20T15:00-07:00
"Auto-approve reimbursements under $50."
[auto_answer:yes agent:pay-agent q~"reimburs" amount<50]
expires_at: null (permanent)
"Anything from Dana is urgent."
[reprioritize:5 source~"Dana"]
expires_at: null (permanent)
"Texts from kids always go to center."
[reprioritize:5 agent:fam tag:kids]
expires_at: null (permanent)
"Don't ask me about code diffs after 7pm."
(recurring — fires every evening)
[snooze:09:00 agent:OpenClaw renderer:diff]
active_window: 19:00–09:00 daily (recurring)

Two ways a rule can expire

  • One-shot with expires_at — the rule has a single ISO-8601 deadline. After that timestamp, the daemon flips its active flag to false. It stays in the store for audit but stops matching. You'll see it greyed-out in the dashboard with a "expired 3h ago" badge; one click reactivates with a new duration if you want.
  • Recurring with active_window — rules like "no code diffs after 7pm" describe a daily window, not a one-time mute. These get a recurring schedule instead of an expires_at, and the dashboard shows them as always-on, currently active or always-on, dormant until 19:00.

The router refuses to compile an ambiguous "15:00" — it needs to be unambiguous from the rule-creation moment. If the LLM can't decide, it returns { error: "ambiguous_time", suggestions: ["today 15:00", "tomorrow 15:00", "every day at 15:00"] } and the dashboard asks you to pick. Better one extra click than a rule that silently rises from the dead.

Rules are explainable — clicking a chip in the dashboard shows the compiled filter, when it was created, when it expires, and the last 5 notifications it matched or blocked. Reversibility matters when an AI is silently intercepting your attention.

08 Dedupe, coalescing, and "this again"

A big risk: an over-eager agent shouts at you 30 times for the same issue. Three layered defenses, in order:

  • Caller idempotency — pass --id or --mute-key. The daemon coalesces inside a 24h window: same key bumps a counter on the existing card instead of stacking.
  • AI semantic dedupe — the router prompt sees open notifications and is asked to identify near-duplicates by meaning. The caller wins ties; the AI only flags, never overrides without looks_like_id being explicitly accepted by the daemon's similarity threshold.
  • User-side — clicking "snooze" or "ack" on a notification with a mute-key teaches the daemon to suppress matching asks for the next N minutes (per-agent, configurable).

09 Deployment topology

The daemon doesn't live on your dev box. It runs in a small VM on a Proxmox server on your home LAN, and every client — long-running agents on the dev box, the dashboard on your phone or tablet, the tray widget on the laptop — reaches it over Tailscale. That setup is the default, not a deployment variant.

What changes about the contract

  • Transport. Default --daemon URL is the daemon's MagicDNS name on your tailnet (https://sjbis.<tailnet>.ts.net), not a Unix socket. The CLI auto-discovers it via tailscale status --json on first run and caches the result, so most callers never set --daemon explicitly.
  • Auth-by-identity, not auth-by-token. Tailscale's daemon tags every inbound request with the calling device's authenticated identity (Tailscale-User-Login, Tailscale-Headers). SJBIS trusts those headers from tailnet IPs and skips bearer-token validation entirely for personal devices. Bearer tokens still exist, but only for agents (so an OpenClaw token can't impersonate Hermes) and for non-tailnet callers (a GitHub webhook firing into the daemon from the public internet).
  • Multi-device dashboard is free. Every client opens its own SSE stream against the same daemon. The daemon fanouts every notification update to all of them, and accepts an answer from whichever one answers first. No CRDTs, no merge resolution — the store is the source of truth, the clients are caches.
  • Latency budget. Proxmox over wired LAN to the dev box: ~0.5 ms. Phone on cellular over Tailscale: 30–60 ms. Both well under the threshold where you'd notice. The only hot path that cares is the dashboard's optimistic answer animation — keep that local-first, then reconcile.
  • Failure modes. Tailnet unreachable from the dev box (kernel update, VPN flap)? Long-running agents hold in-flight asks in their own memory and retry with backoff. Daemon down? Clients show a "sjbis offline · last seen 4m ago" banner; agents keep buffering. Proxmox host dies? That's why the store is a single SQLite file: rsync it elsewhere weekly and you have a recovery path.

Why not run the daemon on the dev box?

Two reasons. First, the dev box reboots and sleeps; the daemon needs to always be up so phones and the watch can answer asks while the laptop is closed. Second, the daemon hosts shared state — history, rules, identity — and putting it on a single workstation makes the multi-device story painful. Proxmox VM is cheap, always-on, and snapshots cleanly.

Why not Cloudflare / a hosted service?

Privacy. The router prompts include the literal question text Stephen is being asked. Those go to Fireworks anyway, but the rest of the data (rules, identity, history, mute keys) never leaves the tailnet. A hosted SJBIS would require sending all of that to a third party. Self-hosted on Proxmox is the cleanest answer.

10 Trust, auth, and the privacy knob

With the deployment story pinned to a Proxmox VM on your tailnet, the trust model has three layers:

  • Tailnet identity (free). Any device on your tailnet is trusted as you. No bearer token needed for the dashboard on your phone, the CLI on your dev box, or the tray widget on your laptop. Revoke a device in Tailscale's admin console and it loses access instantly.
  • Agent tokens (scoped). Long-running agents (OpenClaw, Hermes) call sjbis register --agent-name <name> once and receive a bearer token bound to that name. A Hermes token can post as "Hermes" only — it can't impersonate "OpenClaw", even from the same machine. Revocable individually via sjbis token revoke.
  • Non-tailnet bearer tokens (rare). Things outside your tailnet — a GitHub webhook, a cloud-hosted agent — need explicit per-caller tokens issued by sjbis token issue --label "github-actions" --scope "ask:guard". These tokens are scope-tight and short-lived (90-day default).

The --privacy flag is the fourth axis: it controls how much of the question reaches the LLM provider (Fireworks).

  • public (default) — full question + detail go to the router.
  • redact-pii — names, emails, $ amounts, addresses are masked before the prompt; the dashboard sees the original.
  • private — no AI involvement at all. Urgency is the caller's claim, renderer is the caller's flag, no dedupe.

For the rules engine, the same knob: private means rules must already be compiled (you write JSON directly, not English).

12 Open questions

Do we ever let the caller pre-render?

Probably yes, but later. A caller could ship a small JSX/Web Component snippet for unusual UIs. Risk: arbitrary code in your dashboard. Mitigation: sandbox iframe + capability allow-list. Punt until v1.0.

→ V2 What about voice / phone / Apple Watch?

Good v2 target. The daemon stays the same; only the renderer changes. A watch client renders --yesno and --ack trivially and falls back to "see on desktop" for everything else. Not on the v1 critical path — get the desktop + PWA flow right first.

✓ V1 How does an agent react to a "not now"?

Snooze is a first-class response. The answer envelope carries { snoozed_until: ISO, reason: "..." } instead of an answer value. The caller decides whether to retry at that time or escalate to a different channel. Surfaced in the dashboard as a Snooze button on every renderer (Diff already has it; the others get it for free).

Why not just use macOS Notification Center / Slack / Pushover?

Because SJBIS owns the answer, not just the show. Notification Center can deliver a yes/no banner, but it can't route an approval back to a code agent waiting on stdout. SJBIS is the half of the system that closes the loop, programmatically.

What's the smallest useful v0?

Daemon + CLI + dashboard, no AI router, deterministic rules only. Three days of focused work. The AI router is the high-leverage second move, but it shouldn't be a launch blocker — the contract works without it.
